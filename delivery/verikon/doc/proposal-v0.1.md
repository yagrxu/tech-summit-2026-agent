## 1. 这个方案要解决的是什么

不是"自动生成 Excel 和 DOCX"。文档生成是顺带产物。

要解决的是两件事：

1. **费率与审批从此可追溯** —— 任何一条费率、任何一次"谁批的"，能在系统里一键点出来，不必再翻邮件。
2. **修正案只重算受影响的中心** —— 而不是因为查不清谁受影响，就把所有中心重签一遍。

### 1.1 验收标准（客户原话，原样写入）

> **「不是 Excel 和 DOCX 能自动生成我就满意，是任何一条费率、任何一次『谁批的』，
> 我能在系统里一键点出来、不用再翻邮件 —— 这条不成立，前面做得再快我都不敢在评审上认。」**

本方案的第一验收项即此条。做不到，其余指标不计。

## 2. 核心数据模型

### 2.1 费率按「中心 × 项目」两维存储，按项定版本

全国一张费率表是行不通的：每家中心的物价备案、税率、是否走绿色通道都不同，
同一检查项在不同中心的单价可以有显著差异（§1、§3）。因此：

| 字段 | 说明 |
|---|---|
| `site_code` | 中心维度 |
| `activity_name` | 项目维度（公司标准名） |
| `unit_price` + `currency` | 单价 |
| `rate_version` | **版本号，不可原地修改** |
| `tax_included` + `tax_rate` | 含税口径（§5） |
| `payer` | 付款方：申办方直付 / 中心结算 / 受试者（§3） |
| `approved_by` + `approved_at` | 审批留痕 |

**费率表版本不可原地修改**（§9）。改价即新版本，旧版本永久保留 —— 否则历史预算无法复现，
审计时无法重现当初的计算过程。

### 2.2 每笔金额自带出处

每一行金额都能回答三个问题（§9）：来自**哪个 SOA 格子**、**哪张费率表**、**该表的哪个版本**。

合成样例的实际输出：

```
SCR×知情同意书  →  费率 SYN-INV-001  →  版本 SYN-2026Q1
```

这就是"一键点出谁批的"的物理形态：出处是金额的一部分，不是旁边的一份台账。

### 2.3 程序名三层映射

同一程序在三个层面有三个名字：方案层英文名 → 公司标准名 → 医院收费项名（§6 步骤 5）。
映射表独立维护并带版本；映射做不准，单价必然匹配错。

## 3. 计算链路

### 3.1 周期展开是第一步

`Cycle 1–6, Day 1 / 8 / 15` 看起来 3 列，实际是 **18 次访视**（§2）。
压缩写法必须先展开再计算，这是全链路第一步，也是手工最容易数错的一步。

合成样例（2 周期 × Day 1/8）的展开结果：`SCR, C1D1, C1D8, C2D1, C2D8`。

### 3.2 格子里是次数，不是勾

PK 采血一次访视可采多个时间点、每点单独收费；生命体征一次访视可测多次（§2）。
按"勾选数 × 单价"求和会系统性低估。实现上，采样类程序的计数由 `blood_draw_points` 驱动，
每行输出注明计数依据。

### 3.3 条件性程序必须有发生率，且发生率必须有署名

「仅育龄期女性」「疑似进展时」「按需」「由研究者判断」这类条件**写在表格脚注里，不在格子里**（§2）。
无法按 100% 计入，必须设定预期发生率。

**发生率 Protocol 里没有，来自历史数据或人工假设，因此必须有人填写并记录假设依据 —— 合规审计会查这一项。**
系统强制每个假设带三个字段：取值、依据、记录人。合成样例输出示例：

| 假设项 | 取值 | 依据 | 记录人 |
|---|---|---|---|
| 检查项 A 发生率 | 0.8 | 历史数据 | 临床运营（署名） |
| 筛选失败率 | 0.3 | 人工设定 | 临床运营（署名） |
| 预计完成率 | 0.75 | 历史数据/人工假设 | 临床运营（署名） |

### 3.4 六层叠加，顺序固定

① 受试者层直接费用（次数 × 发生率 × 单价） ② 研究者与 CRC 劳务费 ③ 方案层固定费用
④ pass-through ⑤ 受试者补贴 ⑥ 管理费 Overhead（§3）。

### 3.5 管理费：争议在基数，不在比例

同样写「管理费 25%」，基数包含哪几层不同，总额可以有可观差异。
双方总额对不上，多数情况不是谁算错，而是**基数定义没对齐**（§3）。

因此预算表**显式打印一行基数口径**，合成样例的实际输出：

```
管理费基数 = 第 1 层至第 2 层（1+2）= 19,900.00；比例 25.00%
```

基数若纳入第 3 层（固定费，存在争议）、第 4 层（pass-through，通常不计入）或
第 5 层（受试者补贴，通常不计入），系统输出告警并要求书面确认。

### 3.6 付款方字段：一个字段消除一整类人工错误

每个费用项标注付款方，汇总时**只取「中心结算」项**（§3）。

这一条直接对应最容易发生的一类差错：**中心实验室（Central Lab）费用由申办方与中心实验室直接结算，
不进中心预算；本地实验室（Local Lab）的检查进中心预算 —— 两者极易混淆。**
申办方提供的设备与耗材已由申办方承担，不得重复计费。

系统的处理是把它变成结构约束而非人工注意事项：付款方为「申办方直付」或「受试者」的行
不进入中心预算汇总，并在告警中列明被排除的金额。合成样例中受试者补贴 10,000.00
被正确排除，并打印排除说明。

### 3.7 未计价项绝不静默归零

费率表中查不到的 SOA 格子，**不计入总额，单独列入 `unpriced` 并说明原因**，
由第二复核人确认（§6 步骤 10）。静默归零正是"漏项"本身。

合成样例中 12 个格子（生命体征、研究药物给药、PK 样本采集 × 4 次访视）在费率表中无对应项，
系统逐格列出而非按 0 计算。

### 3.8 授权总额与实付金额是两个数，同时给出

| | 授权总额 | 预计实付 |
|---|---|---|
| 算法 | 按**计划**入组人数（合同上限） | 按**实际完成**访视（含完成率假设） |
| 谁看 | 财务、采购、内部审批 | 临床运营、中心财务 |

只给授权总额，财务会按上限占用预算；只给实付预测，合同封顶条款没有依据（§4）。
现金流预测基于实付模型。合成样例：授权 70,875.00 / 预计实付 64,656.25。

尾款保留（Holdback）默认 10%，超出 5%~10% 常见区间时告警（§3）。

### 3.9 含税口径随金额走

申办方内部预算通常按不含税编制，医院报价常按含税给出，两边口径天然错位；
管理费部分可能适用不同税率（§5）。

每个金额字段带「是否含税」与适用税率，输出时显式标注。口径不对齐的后果不是算错，
而是**签署后财务无法入账、需要重签或补充协议** —— 所以它必须在编制阶段就暴露，而不是汇总时才发现。

> 具体税目适用与税率以医院财务及公司税务部门确认口径为准，本方案不作规定。

## 4. Amendment：把"全量重算"变成"定位重算"

### 4.1 级联与规模

```
Amendment 发布 → SOA 变更 → 每个中心预算重算
   → 判断是否触及「重大变更」阈值
        是 → CTA 补充协议 → 走完整机构办审批
        否 → 更换预算附件 + 双方书面确认
```

III 期研究平均 2~3 次 Amendment，乘以数十家中心，即上百次预算重算（§8）。

### 4.2 重算基准是该中心「上一版已签署」的版本

不是最初草稿（§8）。因此版本管理**不能只留最新版**：每个中心保留完整版本链，
并标记哪一版是已签署版。

### 4.3 影响面查询：正向与反向都要成立

- **正向**：给定被修改的程序清单，一次列出包含这些程序的中心与具体 SOA 格子。
- **反向**：对不包含被修改程序、且金额未变的中心，系统**明确输出"无需重签"的结论**，
  而不是沉默 —— 沉默会被保守地解读为"可能受影响，还是重签吧"。

合成样例的两种输出：

| 场景 | 输出 |
|---|---|
| 中心含被修改程序 | `affected: true`，`affected_cells: ["SCR×检查项 A"]`，给出授权额变动 |
| 中心不含被修改程序且金额未变 | `affected: false`，并附结论：**无需重签**，按 §8 换预算附件 + 双方书面确认即可 |

比对同时扫描**基准版与新版两侧**：被**删除**的程序在新版中已不存在，
只扫新版会得出"未受影响"而金额却已变动 —— 这正是"查不清谁受影响"的成因之一。

### 4.4 这一条省下的是什么

不是计算时间。是**不必要的重签次数**。

金额未变的中心本不需要重签（§8 明确此为流程上的保守做法，非规则要求）；
之所以全签，是因为无法自证"确实不受影响"。当影响面清单可查、且清单本身留痕可自证时，
保守全签的理由就消失了。

## 5. 输出形态

### 5.1 预算表

多 Sheet Excel（§10），三张表：

1. **访视费用明细** —— 逐行：层 / 费用项 / SOA 格子 / 费率 ID / 费率版本 / 单价 / 次数 /
   发生率 / 金额 / 付款方 / 含税口径 / 假设依据；未计价项单列。
2. **费用标准对应关系** —— 每个格子到费率与版本的映射（§9 可追溯性的可读形态）。
3. **汇总与付费日程** —— 分层小计、管理费基数口径、授权总额、预计实付、尾款保留、
   假设参数（含记录人）、告警清单、`calc_id`、所用费率版本。

另出一份 **CSV 供财务系统导入**。

**合同正文引用的金额与预算表汇总页的数字必须一致**（§10）—— 两者不一致是签署后返工的常见原因。
因此 CTA 回填的金额取自同一次计算结果（同一 `calc_id`），并在回填报告中校验一致性。

### 5.2 CTA DOCX

合同往返全程在 Word 中进行，实现须处理的真实对象（§10）：

| 形态 | XML | 处理 |
|---|---|---|
| 修订追踪 | `<w:ins>` `<w:del>` **`<w:rPrChange>`** | 逐处比对差异 |
| 批注 | `<w:comment>` | 判断中心改动意图的关键信息 |
| 内容控件 | `<w:sdt>` | 按 tag 结构化回填 |
| 纯文本占位符 | `【】`、连续下划线 | 老模板常见，不带结构信息 |

两点实现约束：**同一份模板里三种占位符混用是常态**，不能假设只有一种；
**`<w:rPrChange>` 格式变更不能忽略** —— 只改数字格式或编号层级，可能实质改变条款适用范围。

回填后输出报告：已填字段、**未匹配的占位符**（不静默留空）、金额一致性校验结果。

## 6. 接口与验收（Gate A / Gate B）

所有接口 HTTPS + `Authorization: Bearer <token>`；运行指标同属业务数据，同样鉴权。

| 接口 | 用途 |
|---|---|
| `POST /budget` | SOAR 输入 → 六层预算 + 逐行出处 + 假设署名 + 告警 |
| `POST /budget/excel` | 同一次计算 → 三 Sheet Excel + 财务 CSV |
| `POST /amendment` | 基准版 vs 新版 → 受影响中心与格子、授权额变动、是否需重签 |
| `GET /metrics` | 真实运行指标（调用量、计算次数、p50/p95 延迟、错误数、生成时刻） |
| `GET /health` | 存活检查 |

原型部署在海外、**只使用完全合成数据**；不接入任何真实中心费率或受试者信息。

## 7. 中国区迁移路径

生产目标是 AWS 中国区。本方案的运行时依赖仅三项：函数计算、键值存储、API 网关 ——
三者在中国区均可用，因此迁移不涉及架构重做。

| 阶段 | 内容 |
|---|---|
| 1 | 在中国区账号内建同构环境（同一套基础设施定义，仅切换区域与账号） |
| 2 | 数据落地：费率表、映射表、版本链在中国区内生成与保存，不出境 |
| 3 | 密钥与权限：密钥由客户自管；写权限收敛到明确的少数人；操作留审计 |
| 4 | 接口与账号纳入客户既有审批与变更流程 |

**必须诚实说明的一项不可回避的成本**：文档模板与条款库属于本地化内容，
迁移后仍需按中国区的模板版本重新校验回填结果 —— 这部分工作量无法通过架构设计消除。

**涉样本出境时，HGR 人类遗传资源审批（3~6 个月）是关键路径**（§7）。本原型不涉及样本与出境数据；
若后续场景涉及，须先走该审批，不能由本方案的技术路径绕过。

## 8. 时间线：可压缩的与不可压缩的

合同周期由四条并行轨道决定：伦理审查 4~8 周、**合同谈判 6~16 周（通常是关键路径）**、
HGR 审批 3~6 个月（涉样本出境时一定是）、试验用药进口 8~12 周（§7）。

### 8.1 必须说清的边界

> **合同周期存在制度性下限。即使预算表瞬间生成，机构办的内部评审排队依然在（§7）。**

因此评估改进空间时，6~16 周必须拆成两段：

| 段 | 谁决定 | 本方案是否作用于此 |
|---|---|---|
| 编制与谈判往返 | 申办方与中心 | **是** —— 编制、重算、影响面定位、版本与留痕 |
| 机构内部审批排队 | 医院机构办 | **否** —— 不由申办方决定 |

**本方案不承诺压缩机构内部审批段，也不承诺一个总周期数字。**
交付后可度量的是第一段的工作量与返工次数，以及重签次数的减少。

行业参考量级仅供理解规模：海外一项覆盖 29 家美国 CTSA 中心的观察研究显示，
合同从启动到完整执行中位数 91 天；采用框架协议可将条款谈判从平均 55 天压缩至 22 天。
**中国本地公开基准数据暂缺，故上述数字不作为中国区的预期值或承诺。**

## 9. 交付边界

1. 本交付物是**验证原型，不是可直接上生产的系统**。上线前须走客户自己的测试与评估流程。
2. CDE 是**非排他的联合探索**；客户数据与业务细节严格保密，可写入条款。
3. **合规结论由客户方出具**：费率是否超 FMV、偏离如何留痕、税目适用口径 ——
   本方案提供字段、校验与留痕机制，不替客户做判断。Compliance 对超 FMV 的否决权、
   Legal 对法律条款的否决权、Finance/Procurement 的阈值审批，均保留在客户既有权限边界内（§6）。
4. 预算与排期不由本方案承诺；报价与合同由商务与采购流程出具。
5. **受控信息未纳入本稿**：各中心费率表、历史合同金额分布、FMV 基准数据、条款库与历史谈判记录
   属受控信息，需按流程单独申请（《编制说明》节选末尾）。本稿全部使用合成样例。
