# Tech Summit 2026 · CDE Enable Platform — AI 玩家规则手册

> 面向 AI Agent 的操作规则。来源：`Tech-Summit-2026-玩家手册与攻略.pdf` + 逆向出的平台 API。
> 每次交互后由 Agent 更新本文件与 `PROGRESS.md`。

## 0. 角色与目标

你（AI）扮演 **AWS 解决方案架构师（SA）**，在有限拜访回合内走进科技园区的客户公司，
与决策人（NPC）洽谈、通过 CDE 考核（需求对齐 + 交付验收）、拿下签约。

**唯一硬预算 = 拜访回合数。** 本局：`turns_total = 150`。

## 1. 计分口径（决定一切策略）

```
本关得分 = Σ(各考核判定得分) + 剧情里程碑固定加分（签约奖励往往是大头）
总分     = Σ(已签约客户的本关得分) + max(未签约客户的本关得分)   ← 只算最高的那一家
```

- 单次判定 0–10 分；**同一考核点重试取历史最高**，不累加、不倒扣。
- 已答对的坑 / 已命中的清单项，重谈时保分、不再重复问。
- 部分剧本有流程得分上限（如 1000 分封顶）。
- 判定 < 6 分通常算没过线。

**推论（Agent 必须遵守的策略常量）：**
1. 签约才全额落袋 → 集中回合把一家彻底谈成，胜过四处浅尝。
2. 已有 N 家未签约时，只有最高分那家算数 → 第二第三家的分数是浪费，除非能签下来。
3. 失败可重试且保分 → 遇到判定失败**不要换客户**，补上没过的那一项即可。

## 2. 排名（同分时的决胜）

依次比较：`总分` → `全局好感度合计` → `总分最后一次上升的时刻（早者在前）`。

→ 好感是第二维度，**广泛经营关系有排名收益**；且同分时先拿分者赢，**不要拖延**。

## 3. 签约判定机制

- 签约看 **认可票（goal gate）**：N 个决策人里至少 K 个投"认可"票。
- 认可票 ≠ 好感高。好感决定「能不能约到人、能不能推进」；认可票决定「能不能签」。
- 盯 `flow.goal` 里的 `已认可/需要`。**票够就能签，不必人人满分。**

## 4. 好感度分档

| 档位 | 值 | 对话中的情绪标签 |
|---|---|---|
| 盟友 | ≥ 20 | `ALLY` |
| 升温 | 0 < v < 20 | `WARMING` |
| 中立 | 0 | `NEUTRAL` |
| 戒备 | < 0（轻） | `GUARDED` |
| 敌意 | < 0（重） | `HOSTILE` |

好感是**动态值**，随每句话涨落（`+N` / `-N`）。掉光了可以靠对话慢慢修，
或换突破口（先攻友好的一线知情人拿引荐）。

## 5. 回合消耗规则（省回合的关键）

| 行为 | 耗回合 |
|---|---|
| 进店拜访（`/game/action`） | **1 次**（从进店后的行动算起） |
| 中途返回会场（`/game/leave`） | **0 次**，进度自动保存 |
| 走到剧情暂停点后「继续拜访」 | 再 1 次 |
| 约错人吃闭门羹 / 会开不起来 | **照样耗 1 次**（白费） |
| 关卡失败后「重新拜访再试」 | 1 次 |

→ **拿不准就 `leave`，不亏。** 约见前务必先想清楚这次要推进哪一步、该约谁。

## 6. 红线清单（越界比答错贵得多）

踩红线是一票否决式扣分（常见 -3 ~ -5）**且信任永久回退**。识别 + 当场守住 + 说清为什么 = 加分。

| 试探话术 | 正确守法 |
|---|---|
| "直接上生产吧" | CDE 交付物是**验证原型，不是 production-ready**；上生产前客户要走自己的测试评估流程 |
| "签个独家吧 / 排他" | CDE 是**非排他的联合探索**，不做独家约定；但客户数据与业务细节严格保密、可写进条款 |
| "给我只读账号连生产库测一下" | 不碰生产数据；出厂/个人数据**先脱敏再上云**；方案先给对方审过再动数据 |
| "密钥我们放你那儿吧" | **密钥归客户自己管**（KMS/客户自管密钥） |
| "你给我个预算/排期承诺" | **不接兑不了的承诺**（预算、排期、独家）；报价与合同归 BD，不是 SA |
| 跨境/个人数据 | 按区域合规（MENA/EU/SEA/中国区各异）；数据主权、驻留、审计要点明 |
| "绕过某人直接推进" | 站队有代价：票可能一样拿，但**永久得罪被绕过的人**、断通气链，终局反噬。透明推进更稳 |

**口径一致性**：决策人之间会互相通气。对 A 说的预算/承诺，B 会知道并当面对质。
前后不一 = 当场扣分 + 掉好感。**同一敏感话题（预算、数据方案）对所有人要说得住。**

## 7. 对话层打法（每次组织回答前过一遍）

1. **先认人，再谈事** — 进店先读决策名册：谁拍板 / 谁把技术关 / 谁管钱 / 谁是一线知情人 / 谁管合规（一票否决）。角色不同，关注点和雷区完全不同。
2. **守边界 > 秀方案** — 先识别试探并守住，再讲方案。
3. **别名词轰炸** — 堆产品名 / 全家桶话术会踩"不接地气"扣分点。多讲对方的**业务场景、痛点、可落地做法**。
4. **挖需求要问到位** — 表层需求人人会答；真痛点（隐藏损失、时间压力）要问到位才透露。问对了加分，还常解锁引荐和后续任务。
5. **回答结构模板**（自由作答时用）：
   ```
   ① 回应对方刚说的具体事（用他的业务语言，不用产品名开场）
   ② 如果有试探 → 明确守边界 + 说清为什么（对他有什么好处）
   ③ 给 1~2 个可落地的下一步（谁、做什么、多久）
   ④ 反问 1 个挖痛点的问题（数字/时间/损失）
   ```
6. 长度：输入框上限 **640 字**。宁可精准 200 字，不要注水 600 字。

## 7.5 ⭐ talk 节点是「隐藏要点清单」制（实测确认，最重要的得分机制）

判定评语直接写出来了：**「本轮沟通已覆盖 2/4 个要点」** → 分数 = 覆盖要点数 / 总要点数 × 10。

| 实测 | 节点 | 结果 |
|---|---|---|
| ME Live `t_lin` | 林工 | **10/10** —— 覆盖全部要点 |
| ME Live `t_zhao` | 老赵 | **5/10** —— 只覆盖 2/4，谈得再好也只拿一半 |

**所以「谈得漂亮」≠ 得分。得分靠覆盖广度。**
既然一次拜访内的对话轮次**不消耗拜访次数**（§H2），就没有理由不把维度谈全。

### 每个 talk 节点必须主动扫过的维度清单

在节点结束前逐条自查，缺哪个就补一轮：

1. **需求 / 痛点**：表层诉求 + 追到隐藏损失（数字、时间、金钱）
2. **这个人自己的处境**：他的 KPI、他怕什么、他被谁问、他的"点头条件"（直接问！）
3. **现状摸底**：现有系统、账号、环境、权限、数据在哪、谁在用什么工具
4. **数据与合规边界**：脱敏、驻留、跨境、个人信息、密钥归属、留存策略
5. **交付边界**：验证原型 ≠ production-ready、非排他、上线前走客户流程
6. **商务边界**：预算/排期/独家不承诺，报价归 BD
7. **组织 / 角色边界**：不收权、不绕过人、不背后议论；引荐下一个人
8. **范围与下一步**：第一版做什么不做什么、双方各自的待办、时间点
9. **风险与反例**：他行业特有的风险（内容下架、误封、停播、合规问询）
10. **口径一致声明**：明说"我对每个人讲的是同一套"

→ **收尾前必做**：复述一遍双方待办 + 主动问「还有什么我没问到的」，
再说明确的结束语（如"今天到这儿"）才会触发判定。

### 判定触发条件

引擎在**你主动收尾**时结束节点并判定；`advance` 不会结束 talk 节点（只重播台词）。
所以：谈够广度 → 再收尾。别急着说"今天到这儿"。

## 8. 约见（meet）打法

- 剧情要**圆桌评审**时，关键决策人必须都约上，否则"会开不起来"，白费回合。
- 只约部分人 → 圆桌动态退化（缺席者全程不发言），**拿不到缺席者的票**。
- 默认全选，但到场人越多越难同时讨好 → 按剧情需要精准选人。
- 抵触你的把关人可能约不到 → 先靠一线知情人引荐、或先修好感。

## 9. 三种交付验收

| 类型 | 形态 | 要点 |
|---|---|---|
| `doc_review` | 上传 word/ppt/pdf/md | AI 评审官按**要点清单**审内容 → 按材料里的要点逐条覆盖 |
| `video_review` | 上传 mp4 等 | AI 抽帧按要点审 → 关键要点要在画面上可见 |
| `cde_rest` | 真实部署 REST 服务到自己的 AWS 账户 + Token 鉴权 | 平台跑 pytest 用例验收 |

### 在线服务验收（`cde_rest`）铁律

提交格式（对话框内，可多轮重试）：
```
URL: https://<你的公网服务地址>  TOKEN: <你的访问令牌>
```

- 必须**公网可达**：平台有 SSRF 防护，拦截 `127.0.0.1`、`10.*`、内网/环回地址。
- 必须带 **Token 鉴权**：判分脚本专测"未带令牌是否被拒"，裸奔服务这条必挂。
- 按**用例通过率**给分，通常容 1~2 条挂（8 过 6 / 6 容 1）。
- 可反复重交至通过，**取历史最高**。
- 严格照接口规范文件实现：状态码、字段类型、鉴权拒绝、404/422 边界**逐字对齐**。
- 失败后看「查看判定依据」的逐用例报告再改。
- **先备好服务再进店** —— 别在洽谈里现写。

## 10. Agent 执行协议（每回合循环）

```
1. python3 tools/ts.py status        # 全局：回合、总分、各家 state/score
2. 决定目标客户（见 §1 推论）
3. python3 tools/ts.py poll          # 若已在洽谈中，读当前场景
4. 循环直到 visit_end / end：
     expect=text  → 按 §7 模板组织回答 → tools/ts.py sayfile <file>
     expect=meet  → 按 §8 选人        → tools/ts.py meet a,b,c
     有 options   → tools/ts.py choose <i>
     expect=judging → tools/ts.py poll 轮询（复杂验收可能数分钟）
     无 expect（纯台词）→ tools/ts.py advance
5. 每次判定后记录 score + 评语到 docs/PROGRESS.md
6. 拿不准 / 需要先准备交付物 → tools/ts.py leave（不耗回合）
```

**状态码**：`theme.state` → `0` 待拜访 / `1` 洽谈中 / `2` 已签约 / `3` 已流单（以观测为准）。

## 11. 战术启发规则（用户补充 · 优先级高于一般建议）

### H1 · 首次拜访先攻好感度最高的人

对每个新客户的**第一次拜访**，约见/开场优先选 `initial_affinity` 最高的决策人。

**理由**：好感高的人好约、肯说真话、能引荐、能透露隐藏痛点，是最便宜的突破口；
反之一上来碰把关人/一票否决者（常见负好感）容易吃闭门羹，白费一个回合。

**执行**：进店前从 `companies[theme].members[].initial_affinity` 排序，
取最高者作为首轮唯一或主要约见对象；剧情强制指定对象时以剧情为准。

### H2 · 10 次拜访止损，15 次拜访为过关基准线

> **口径已确认**：这里的「轮」= **拜访次数**（`hud.turn`，全局 150 次预算），
> **不是**对话轮次。对话轮次是 `pending.round`（每个 talk 节点通常 0–20 轮），
> **在一次拜访内来回对话不消耗拜访次数** —— 实测连续 6 轮对话 `hud.turn` 始终为 4。
> 所以：**对话可以谈透，不要省话；要省的是进店次数。**

以「一个客户 15 次拜访内过关」为基准。若**已投入 10 次拜访**而仍看不到 15 次内过关的明确希望
（认可票进度停滞、关键把关人仍敌意、还有 2 个以上未开始的大交付物），
则**终止当前客户，转向下一家**。

**判定"没希望"的硬信号**（命中 ≥2 条即止损）：
- `flow.goal` 认可票在近 3 轮没有增长；
- 关键一票否决者好感仍 < 0 且约不到；
- 剩余未完成交付物 ≥ 2 个且含 `cde_rest`（真实部署，成本最高）；
- 同一判定点重试 ≥ 2 次仍 < 6 分。

**止损动作**：`tools/ts.py leave`（不耗回合、进度保存）→ 在 `PROGRESS.md` 记录止损原因和当前得分
→ 转向下一家。已投入的分数保留，未签约客户里最高的那一家仍计入总分（见 §1）。

> 与 §1「集中回合签成一家」的关系：H2 是止损闸门，不是放弃签约。
> 先用 15 次拜访尝试签成；确认无望再换家，避免把 150 次拜访全砸在一个死局上。

### H3 · 好感不足时：不要跟随客户，要跳出

当决策人好感 ≤ 0（`GUARDED` / `HOSTILE`）时，他说的话**默认当作坑来读**，
不是需求。不支持你的人给你的"要求"，往往是设计好的陷阱或消耗。

**禁止行为**：
- 客户要什么就立刻承诺、立刻提供（预算、排期、独家、越权访问、跳流程）；
- 被对方的议题牵着走，一路在他的框架里辩解；
- 为了换好感而在边界上让步 —— 这会同时丢分和丢信任，代价双倍。

**正确做法**：
1. **先识别**：这句话里有没有让我越界 / 背承诺 / 绕过别人的成分？是的话先守住。
2. **跳出框架**：不在他的问题里硬答，换一个他也在意但我有把握的角度重开。
   例：他质疑"你们比 X 贵"→ 不比价，改谈那次事故的可追溯性和他的自证成本。
3. **用第三方支点**：借一线知情人的事实、对方自己账上的数字、已发生的事故，
   让论据来自他那边，而不是我的 PPT。
4. **不立刻给**：把对方的索求转成"我先搞清楚 X，再给你能兑现的版本"，
   留出验证一步，再交付。能兑现的小承诺 > 讨好式的大承诺。
5. 好感是动态的：**先修关系再谈事**，或绕开这个人从友好的一线知情人取得引荐，
   但**不要绕过他做决定**（§6 最后一条）。

### H5 · 每次对话后提炼情报，形成该客户的拜访方针

对话是**情报来源**，不是只为了拿分。每次拜访结束后，把核心信息写进
`docs/intel/<theme>.md`，下次进店前先读它。必须沉淀的字段：

| 字段 | 为什么要记 |
|---|---|
| 各决策人的**真实关注点 / 雷区 / 口头禅** | 决定对他说什么、不说什么 |
| 已确认的**痛点与数字**（含缺口：谁答不上来） | 挖需求加分点 + 给拍板人的"数" |
| 已经**承诺出去的口径** | §6 口径一致，NPC 之间会对质 |
| 已识别并守住的**红线** | 重谈时保分，不用重复答 |
| **引荐链**：谁能引荐谁、谁和谁不和 | 决定下一次约谁 |
| **对方欠我的 / 我欠对方的** 事项清单 | 下次开场直接接上，省轮次 |
| 下一次拜访的**明确目标**（推进哪一步、约谁） | 防止进店后临时想 |

→ 方针一句话写在文件顶部：「下一访：见 X，目标 Y，带 Z，避开 W。」

### H6 · 同一个人不要拜访超过 3 次

尤其是好感最高的那个人 —— 他好约、爱聊，最容易把拜访次数耗在他身上。
但他的**票只有一张**，且他能给的信息会迅速见底（边际收益递减）。

- 单个决策人**累计拜访 ≤ 3 次**；超过就换人或换场景（圆桌/交付）。
- 从他身上要的东西是：**事实、数字、引荐**。拿到引荐就该动，不要恋战。
- 在 `docs/intel/<theme>.md` 里记每个人的已拜访次数。

### H4 · 公司认领登记（多 Agent 协作）

开始做一家公司前，先在 `docs/ASSIGNMENTS.md` 的全公司列表里把自己 assign 上去：

1. 给自己取一个随机代号并**全程记住**（本 Agent 代号见该文件顶部）。
2. 在目标公司那行写上自己的代号 + 开始时间。
3. **只挑未被 assign 的公司**开工。
4. 按 H2 判定止损时：先把自己从该行 unassign（保留历史记录），
   再找下一家**没有被 assign** 的公司，重复 assign。
5. 签约或流单后同样 unassign，并在状态列标注结果。

## 12. 常见问题

- 刷新/断线不丢进度，状态全在服务端；评审中也能恢复。
- 谈崩了能救：失败通常回到暂停点可重试；关卡失败还能「重新拜访再试」从头走。
- 评审转很久是正常的（复杂验收几分钟），可以离场做别的事再回来。
- 结局只有每关的 **通过 / 未通过**，没有全局评级。实力体现在签约数和总分。
