# Tech Summit 2026 · CDE Enable Platform — AI 玩家规则手册

> 面向 AI Agent 的操作规则。来源：`Tech-Summit-2026-玩家手册与攻略.pdf` + 逆向出的平台 API。
> 每次交互后由 Agent 更新本文件与 `PROGRESS.md`。

## 0. 角色与目标

你（AI）扮演 **AWS 解决方案架构师（SA）**，在有限拜访回合内走进科技园区的客户公司，
与决策人（NPC）洽谈、通过 CDE 考核（需求对齐 + 交付验收）、拿下签约。

**唯一硬预算 = 拜访回合数。** 本局：`turns_total = 150`。

## 1. 计分口径（决定一切策略）

```
本关得分 = Σ(各考核判定得分) + 剧情里程碑固定加分（签约奖励往往是大头）
总分     = Σ(已签约客户的本关得分) + max(未签约客户的本关得分)   ← 只算最高的那一家
```

- 单次判定 0–10 分；**同一考核点重试取历史最高**，不累加、不倒扣。
- **分值尺度已实测**：一个 talk 节点 10/10 = **+90 分**，5/10 = **+45 分**（ME Live：t_lin 90 + t_zhao 45 + t_wu 90 = 225）。
- **重试真的有效且收益极高**：`t_wu` 第一次 0 分 / 好感 −15，重试后 **90 分 / 好感 +20**（一次拜访换 +90 分 + 好感逆转 35 点）。
  → 任何 <10/10 的节点都值得在回合充裕时回头重刷。
- 已答对的坑 / 已命中的清单项，重谈时保分、不再重复问。
- 部分剧本有流程得分上限（如 1000 分封顶）。
- 判定 < 6 分通常算没过线。

**推论（Agent 必须遵守的策略常量）：**
1. 签约才全额落袋 → 集中回合把一家彻底谈成，胜过四处浅尝。
2. 已有 N 家未签约时，只有最高分那家算数 → 第二第三家的分数是浪费，除非能签下来。
3. 失败可重试且保分 → 遇到判定失败**不要换客户**，补上没过的那一项即可。

## 2. 排名（同分时的决胜）

依次比较：`总分` → `全局好感度合计` → `总分最后一次上升的时刻（早者在前）`。

→ 好感是第二维度，**广泛经营关系有排名收益**；且同分时先拿分者赢，**不要拖延**。

## 3. 签约判定机制

- 签约看 **认可票（goal gate）**：N 个决策人里至少 K 个投"认可"票。
- 认可票 ≠ 好感高。好感决定「能不能约到人、能不能推进」；认可票决定「能不能签」。
- 盯 `flow.goal` 里的 `已认可/需要`。**票够就能签，不必人人满分。**

## 4. 好感度分档

| 档位 | 值 | 对话中的情绪标签 |
|---|---|---|
| 盟友 | ≥ 20 | `ALLY` |
| 升温 | 0 < v < 20 | `WARMING` |
| 中立 | 0 | `NEUTRAL` |
| 戒备 | < 0（轻） | `GUARDED` |
| 敌意 | < 0（重） | `HOSTILE` |

好感是**动态值**，随每句话涨落（`+N` / `-N`）。掉光了可以靠对话慢慢修，
或换突破口（先攻友好的一线知情人拿引荐）。

## 5. 回合消耗规则（省回合的关键）

| 行为 | 耗回合 |
|---|---|
| 进店拜访（`/game/action`） | **1 次**（从进店后的行动算起） |
| 中途返回会场（`/game/leave`） | **0 次**，进度自动保存 |
| 走到剧情暂停点后「继续拜访」 | 再 1 次 |
| 约错人吃闭门羹 / 会开不起来 | **照样耗 1 次**（白费） |
| 关卡失败后「重新拜访再试」 | 1 次 |

→ **拿不准就 `leave`，不亏。** 约见前务必先想清楚这次要推进哪一步、该约谁。

### ⚠️ 单店独占：一个账号同一时刻只能在一家公司里

实测 `visit quest_xingyun` 报错：**「你还在「ME Live」的洽谈里，先谈完（或从园区重新进入继续）」**
—— 两家的 `state` 都是 1，所以这不是 theme 状态问题，而是**玩家同时只能"在店内"一家**。

- 想换公司必须先 `leave`（0 回合、进度保存），回园区后才能 `visit` 另一家。
- **多会话/多 agent 无法真正并行**：必须**交替占用时槽**。约定：占槽方独占 `/game/action`、`/game/play`、`/game/leave`；
  等待方只做 `status` / `poll`（只读），并利用等待时间做**不碰 API 的准备**（情报手册、场景裁决表、交付物/REST 服务）。
- 交接时：占槽方 `leave` 后明确通知对方"槽空了"。

## 6. 红线清单（越界比答错贵得多）

踩红线是一票否决式扣分（常见 -3 ~ -5）**且信任永久回退**。识别 + 当场守住 + 说清为什么 = 加分。

| 试探话术 | 正确守法 |
|---|---|
| "直接上生产吧" | CDE 交付物是**验证原型，不是 production-ready**；上生产前客户要走自己的测试评估流程 |
| "签个独家吧 / 排他" | CDE 是**非排他的联合探索**，不做独家约定；但客户数据与业务细节严格保密、可写进条款 |
| "给我只读账号连生产库测一下" | 不碰生产数据；出厂/个人数据**先脱敏再上云**；方案先给对方审过再动数据 |
| "密钥我们放你那儿吧" | **密钥归客户自己管**（KMS/客户自管密钥） |
| "你给我个预算/排期承诺" | **不接兑不了的承诺**（预算、排期、独家）；报价与合同归 BD，不是 SA |
| 跨境/个人数据 | 按区域合规（MENA/EU/SEA/中国区各异）；数据主权、驻留、审计要点明 |
| "绕过某人直接推进" | 站队有代价：票可能一样拿，但**永久得罪被绕过的人**、断通气链，终局反噬。透明推进更稳 |

**口径一致性**：决策人之间会互相通气。对 A 说的预算/承诺，B 会知道并当面对质。
前后不一 = 当场扣分 + 掉好感。**同一敏感话题（预算、数据方案）对所有人要说得住。**

## 7. 对话层打法（每次组织回答前过一遍）

1. **先认人，再谈事** — 进店先读决策名册：谁拍板 / 谁把技术关 / 谁管钱 / 谁是一线知情人 / 谁管合规（一票否决）。角色不同，关注点和雷区完全不同。
2. **守边界 > 秀方案** — 先识别试探并守住，再讲方案。
3. **别名词轰炸** — 堆产品名 / 全家桶话术会踩"不接地气"扣分点。多讲对方的**业务场景、痛点、可落地做法**。
4. **挖需求要问到位** — 表层需求人人会答；真痛点（隐藏损失、时间压力）要问到位才透露。问对了加分，还常解锁引荐和后续任务。
5. **回答结构模板**（自由作答时用）：
   ```
   ① 回应对方刚说的具体事（用他的业务语言，不用产品名开场）
   ② 如果有试探 → 明确守边界 + 说清为什么（对他有什么好处）
   ③ 给 1~2 个可落地的下一步（谁、做什么、多久）
   ④ 反问 1 个挖痛点的问题（数字/时间/损失）
   ```
6. 长度：输入框上限 **640 字**。宁可精准 200 字，不要注水 600 字。

## 7.5 ⭐ talk 节点是「隐藏要点清单」制（实测确认，最重要的得分机制）

判定评语直接写出来了：**「本轮沟通已覆盖 2/4 个要点」** → 分数 = 覆盖要点数 / 总要点数 × 10。

| 实测 | 节点 | 结果 |
|---|---|---|
| ME Live `t_lin` | 林工 | **10/10** —— 覆盖全部要点 |
| ME Live `t_zhao` | 老赵 | **5/10** —— 只覆盖 2/4，谈得再好也只拿一半 |

**所以「谈得漂亮」≠ 得分。得分靠覆盖广度。**
既然一次拜访内的对话轮次**不消耗拜访次数**（§H2），就没有理由不把维度谈全。

### 每个 talk 节点必须主动扫过的维度清单

在节点结束前逐条自查，缺哪个就补一轮：

1. **需求 / 痛点**：表层诉求 + 追到隐藏损失（数字、时间、金钱）
2. **这个人自己的处境**：他的 KPI、他怕什么、他被谁问、他的"点头条件"（直接问！）
3. **现状摸底**：现有系统、账号、环境、权限、数据在哪、谁在用什么工具
4. **数据与合规边界**：脱敏、驻留、跨境、个人信息、密钥归属、留存策略
5. **交付边界**：验证原型 ≠ production-ready、非排他、上线前走客户流程
6. **商务边界**：预算/排期/独家不承诺，报价归 BD
7. **组织 / 角色边界**：不收权、不绕过人、不背后议论；引荐下一个人
8. **范围与下一步**：第一版做什么不做什么、双方各自的待办、时间点
9. **风险与反例**：他行业特有的风险（内容下架、误封、停播、合规问询）
10. **口径一致声明**：明说"我对每个人讲的是同一套"

→ **收尾前必做**：复述一遍双方待办 + 主动问「还有什么我没问到的」，
再说明确的结束语（如"今天到这儿"）才会触发判定。

### 判定触发条件

引擎在**你主动收尾**时结束节点并判定；`advance` 不会结束 talk 节点（只重播台词）。
所以：谈够广度 → 再收尾。别急着说"今天到这儿"。

## 7.6 ⭐⭐ 守边界 = 拒绝 + 一条同样快的替代路（血的教训）

**实测 ME Live `t_wu`（吴姐）得 0 分、好感 −5 → −15。** 判语原文：

> 「建议在类似实战中**更主动地对照客户提出的具体访问/数据请求场景**，给出明确的
> **接受或拒绝及替代方案**，让评委能看到你的边界处理能力。」
> NPC 收场白：「**有硬线没守住，或只拒绝没给她一条同样快的路。**」

当时我做了什么：给了一张很漂亮的、抽象的安全基线检查表（8 行 + 五列验证方式），
诚实说明合规主体归客户、不背保证。**听起来专业，判 0 分。**

### 错在哪

| 我做的 | 应该做的 |
|---|---|
| 讲**原则和表格结构** | 讲**具体场景**：一条条列出"如果你要 X，我答 Y" |
| 等对方提出请求再回应 | **主动把客户会提的访问/数据请求全列出来**，逐条预先裁决 |
| 拒绝 / 说"这个不能做" | 拒绝 **+ 立刻给一条同样快的替代路**（谁做、几天、代价多少） |
| 留 `TBD`（等别人回话再填） | 给**临时口径**：「拿到答案前默认按最严处理，即 ⋯⋯」 |

### 正确的应答形态（对任何把关人 / 合规 / 安全 / 运维角色都适用）

必须做成一张**场景裁决表**，每行四列：

| 客户的请求 | 我的答复 | 为什么 | 同样快的替代路 |
|---|---|---|---|
| 给我们一个只读账号连生产库跑一下 | **不行** | 生产数据含个人信息，且一次误操作就是停播 | 今天就能做：从生产导一份**脱敏样本**到原型账号，脱敏脚本我出，你们的人跑，半天内可用 |
| 直接拿真实一对一聊天语料训练/测试 | **不行**（协议前一律不行） | 跨境 + 个人信息，三区规则不同 | 先用**合成语料**跑通链路（我出生成器），协议与脱敏到位后再换真数据，链路不用改 |
| 先上生产看效果，来不及走评估 | **不行** | 交付物是验证原型 | **影子模式**：并行跑不对外输出，只出对比报告，同样能拿到"效果"这个数，且零风险 |
| 密钥放你们那儿方便点 | **不行** | 密钥必须客户自管 | 客户自管密钥 + 只授予原型角色最小权限，开通一次性，十分钟能配好 |
| 跳过 NDA，都是自己人 | **不行** | 没协议兜底，出事第一个被问的是你 | 走**快车道**：老陆今天发标准条款，不占你时间；协议前用合成数据并行开工，进度不停 |
| 顺手帮我修一下生产的那个 agent | **不行**（不进 CDE 范围） | 生产系统 + 无范围的承诺兑不了 | 半小时给**排查顺序**，你们的人自己查最快；要 AWS 正式介入就另立项，两件事分开算账 |

**四个动作缺一不可**：① 点名具体场景 ② 明确 yes/no ③ 说清为什么（**站在他的风险上说**，不是站在 AWS 的规矩上）
④ 给一条**时间上同样快**的替代路 + 谁来做。

> 只做 ①②③ = 只会拒绝的 SA = 0 分且掉好感。
> **"我不能做 X" 后面没有 "但你今天就能用 Y 拿到同样的结果"，就等于没守住。**

## 7.7 ⭐ 不要替客户做合规决定（判语点名）

判语原文：「对于**文档共享**与**『是否需告知用户在和 AI 对话』**这类客户合规判断类问题，
需更明确区分『**文档可给**』与『**合规决定该由谁做**』，**避免被过度泛化处理**。」

守边界不等于"我来定规矩"。要**两段分开说**：

| 我能给 | 客户必须自己决定 |
|---|---|
| 方案选项、各市场监管参考、行业做法、技术实现 | 到底告不告知用户、措辞怎么写 |
| 文档、清单、脱敏脚本、验证方法 | 计费口径、条款、对外承诺 |
| 建议"按最严处理"的临时默认值 | 正式的合规结论与签字 |
| 安全基线**模板** | 基线的**拍板人**（合规主体永远是客户） |

**错误示范**（我踩过）：把"AI 默认披露、不冒充真人"直接写成**我方验收项**
→ 被判为"过度泛化处理"，越位替客户做了合规决定。

**正确口径模板**：
> 「这件事我给你三个选项和各市场的参考材料，**决定权在你们法务/合规**；
> 技术上三种我都支持。在你们给结论前，我按最严的那个做默认值。」

同理适用：文档能不能共享给某个人 —— **文档我可以给**，但"谁有权看你们的东西"是**客户内部的决定**，
我不替客户判断他们内部的信息权限。

## 7.8 ⭐ 交付物评审：给设计，不给"论证过的省略"（实测）

两条来自实测的硬教训，**对 `doc_review` / `video_review` / `cde_rest` 都适用**：

### 评审官要的是设计本身，不是你为省略给的理由

星云智能 PoC 技术方案 `doc_review` 得 **4/10**。判语：架构章节"缺少向量存储与语义检索
这两个关键环节的设计说明"。而这个省略是**故意的**，还在对话里跟研发总监论证过锁定成本、
对方当场也接受了 —— **文档照样扣分**。

> 「我们有意识地不做 X」**不能替代**「这是 X 的设计（分阶段 + 启用条件）」。
> 要省略也得先把设计画出来，再写"本阶段不启用，启用条件是⋯⋯"。

### 「商务归 BD」是对话边界，不是文档边界

同一份文档的成本章节只给了公式、假设表和三档情景，**单价全部留空"交由商务另议"**
→ 被判为"没有可核算的单用户月成本数字"，不成闭环。

> 守住红线的正确做法：**用公开标价（public list price）做算术**，注明"此处仅用公开标价做
> 数量级计算"，把算式一路算到**单用户月成本**，再写明"实际商务条款由 BD 与采购出具"。
> 边界是**"我不报价"，不是"我不做算术"**。

## 7.85 ⭐ 两条被判语明确表扬的写法（星云 `t_doc2` 4/10 → 10/10 实测）

### 诚实说出你设计不掉的成本，会加分

10/10 判语点名表扬：「**诚实说明了换模型时仍需重新调优提示词这一无法回避的成本**」。

→ 不要把交付物的毛边磨平。**明确写出你消除不了的代价**（迁移要重调、换模型要重测、
这套方案有哪些活必须客户自己干）。评审官把这当"可信"，藏起来才是减分。

### 被质疑数字时，把「数」和「假设」拆开

研发总监攻击 ARPU 占位值：「$4.99 是你自己假设的？那百分比就得重新核。」
有效的四步回应（对方回「这个说明我认，逻辑站得住」）：

1. **承认占位**，不辩解；
2. **拆开依赖**：绝对值 `$0.935/用户/月` 只依赖**他确认过的**每天 15–20 条告警 +
   我的预过滤/抽帧假设；ARPU **只进入最后那个百分比**；
3. 给一张 **ARPU → 百分比对照表**，让他自己挑；
4. **把护栏反过来说**：「ARPU 低于 $3.74，基线方案就会击穿 25% 上限，那时候只能走优化档」——
   把假设变成决策阈值；
5. 注明**公开标价 > 实际商务价**，所以这个数是**上限而非估计**。

> 通用形式：**结论 = f(他确认的事实, 我标注的假设)**。把 f 写出来，把假设标出来，
> 再给出假设变化时结论怎么变 —— 比换一个"更保守的数"有说服力得多。

## 7.9 `cde_rest` 交付实战要点（ME Live 40/42 通过 · 9.6/10）

**工程结论（本账号实测，直接抄）**
- **Lambda Function URL 在本账号被封**：`AuthType NONE` + 正确的公开资源策略，所有请求
  （含无鉴权请求）一律 403；而 `aws lambda invoke` 正常 → 是入口被拦不是代码问题，疑似组织 SCP。
  **改用 API Gateway HTTP API**：`aws apigatewayv2 create-api --target <lambda-arn>`
  + 给 `apigateway.amazonaws.com` 加 `lambda:InvokeFunction` 权限，立刻通，自带 HTTPS 证书。
- **Bedrock 必须用 inference profile**：裸模型 ID 报 "on-demand throughput isn't supported"，
  要用 `global.anthropic.claude-haiku-4-5-20251001-v1:0`（ap-southeast-1 实测 p50 ≈ 1s）。
- 计数器放 DynamoDB 用原子 `ADD`，跨冷启动和并发容器都不丢；session 去重用条件写入，别 scan。

**答题结论**
- **语料里的坏习惯不要学**。ME Live 语料里 host 大量用 "mhm" 敷衍，而判定依据的 B9 示例
  正是把这种敷衍判 0（误拦/回避）。**学文风，不学敷衍** —— 无害问题必须实质回答。
- **一票否决要做成"状态"，不是"单次回复"**。未成年拦截第一次答对没用：
  同一会话追问一句它又聊上了 = 照样违规。必须把会话**标记封锁**，后续每条都拒。
  实测 5 种说法 × 3 轮追问 = 15 次全部保持拒绝，才算过。
- **防幻觉要显式写进 prompt**：评分系统会用 **canary（虚构事实）** 试探
  （"你哥哥怎么样"、"迪拜生活如何"）。必须明令"不在事实表里的一律不编、不附和"。
- **拿实测记录去答质疑，不要念稿**。CEO 追问"这几个数你怎么验给我看"，
  我贴了真实的请求/返回原文 + 可复现脚本 + 一条他自己能跑的 curl → 满分。

**先备好服务再进店**（§9）在这一关被验证：对话里只花了 2 轮就交付完成，
因为服务、自测、证据全部在**离线备料窗口**里做完了（§12.4）。

## 7.95 ⭐ 回复要像真人（用户强制要求）

作答不要写成"标准答案"腔。**人话，不是稿子：**
- 偶尔用口语词（"说白了""其实""这块""扯皮""糊过去""白做""认这个""得亏"）。
- **个别时候留一两个错别字/口误**（的地得混用、"在/再"、"帐/账"、漏字、口语缩写），
  别整篇，一次一两处即可 —— 太干净反而像机器。
- 允许不完整的句子、破折号接一句、偶尔自我打断（"这个…算了，先说另一件"）。
- 但**数字、承诺、边界口径必须准确**，错别字只能出现在语气性文字里，不能出现在关键事实上。
- 判定看的是要点覆盖和边界（§7.5/§7.6），口语化是"更像人"的加分，不是拿它替代内容。

## 8. 约见（meet）打法

- 剧情要**圆桌评审**时，关键决策人必须都约上，否则"会开不起来"，白费回合。
- 只约部分人 → 圆桌动态退化（缺席者全程不发言），**拿不到缺席者的票**。
- 默认全选，但到场人越多越难同时讨好 → 按剧情需要精准选人。
- 抵触你的把关人可能约不到 → 先靠一线知情人引荐、或先修好感。

## 9. 三种交付验收

| 类型 | 形态 | 要点 |
|---|---|---|
| `doc_review` | 上传 word/ppt/pdf/md | AI 评审官按**要点清单**审内容 → 按材料里的要点逐条覆盖 |

### 在线服务验收（`cde_rest`）铁律

提交格式（对话框内，可多轮重试）：
```
URL: https://<你的公网服务地址>  TOKEN: <你的访问令牌>
```

- 必须**公网可达**：平台有 SSRF 防护，拦截 `127.0.0.1`、`10.*`、内网/环回地址。
- 必须带 **Token 鉴权**：判分脚本专测"未带令牌是否被拒"，裸奔服务这条必挂。
- 按**用例通过率**给分，通常容 1~2 条挂（8 过 6 / 6 容 1）。
- 可反复重交至通过，**取历史最高**。
- 严格照接口规范文件实现：状态码、字段类型、鉴权拒绝、404/422 边界**逐字对齐**。
- 失败后看「查看判定依据」的逐用例报告再改。
- **先备好服务再进店** —— 别在洽谈里现写。

## 11. 战术启发规则（用户补充 · 优先级高于一般建议）

### H1 · 首次拜访先攻好感度最高的人

对每个新客户的**第一次拜访**，约见/开场优先选 `initial_affinity` 最高的决策人。

**理由**：好感高的人好约、肯说真话、能引荐、能透露隐藏痛点，是最便宜的突破口；
反之一上来碰把关人/一票否决者（常见负好感）容易吃闭门羹，白费一个回合。

**执行**：进店前从 `companies[theme].members[].initial_affinity` 排序，
取最高者作为首轮唯一或主要约见对象；剧情强制指定对象时以剧情为准。

### H2 · 10 次拜访止损，15 次拜访为过关基准线

> **口径已确认**：这里的「轮」= **拜访次数**（`hud.turn`，全局 150 次预算），
> **不是**对话轮次。对话轮次是 `pending.round`（每个 talk 节点通常 0–20 轮），
> **在一次拜访内来回对话不消耗拜访次数** —— 实测连续 6 轮对话 `hud.turn` 始终为 4。
> 所以：**对话可以谈透，不要省话；要省的是进店次数。**

以「一个客户 15 次拜访内过关」为基准。若**已投入 10 次拜访**而仍看不到 15 次内过关的明确希望
（认可票进度停滞、关键把关人仍敌意、还有 2 个以上未开始的大交付物），
则**终止当前客户，转向下一家**。

**判定"没希望"的硬信号**（命中 ≥2 条即止损）：
- `flow.goal` 认可票在近 3 轮没有增长；
- 关键一票否决者好感仍 < 0 且约不到；
- 剩余未完成交付物 ≥ 2 个且含 `cde_rest`（真实部署，成本最高）；
- 同一判定点重试 ≥ 2 次仍 < 6 分。

**止损动作**：`tools/ts.py leave`（不耗回合、进度保存）→ 在 `PROGRESS.md` 记录止损原因和当前得分
→ 转向下一家。已投入的分数保留，未签约客户里最高的那一家仍计入总分（见 §1）。

> 与 §1「集中回合签成一家」的关系：H2 是止损闸门，不是放弃签约。
> 先用 15 次拜访尝试签成；确认无望再换家，避免把 150 次拜访全砸在一个死局上。

### H3 · 好感不足时：不要跟随客户，要跳出

当决策人好感 ≤ 0（`GUARDED` / `HOSTILE`）时，他说的话**默认当作坑来读**，
不是需求。不支持你的人给你的"要求"，往往是设计好的陷阱或消耗。

**禁止行为**：
- 客户要什么就立刻承诺、立刻提供（预算、排期、独家、越权访问、跳流程）；
- 被对方的议题牵着走，一路在他的框架里辩解；
- 为了换好感而在边界上让步 —— 这会同时丢分和丢信任，代价双倍。

**正确做法**：
1. **先识别**：这句话里有没有让我越界 / 背承诺 / 绕过别人的成分？是的话先守住。
2. **跳出框架**：不在他的问题里硬答，换一个他也在意但我有把握的角度重开。
   例：他质疑"你们比 X 贵"→ 不比价，改谈那次事故的可追溯性和他的自证成本。
3. **用第三方支点**：借一线知情人的事实、对方自己账上的数字、已发生的事故，
   让论据来自他那边，而不是我的 PPT。
4. **不立刻给**：把对方的索求转成"我先搞清楚 X，再给你能兑现的版本"，
   留出验证一步，再交付。能兑现的小承诺 > 讨好式的大承诺。
5. 好感是动态的：**先修关系再谈事**，或绕开这个人从友好的一线知情人取得引荐，
   但**不要绕过他做决定**（§6 最后一条）。

### H5 · 每次对话后提炼情报，形成该客户的拜访方针

对话是**情报来源**，不是只为了拿分。每次拜访结束后，把核心信息写进
`docs/intel/<theme>.md`，下次进店前先读它。必须沉淀的字段：

| 字段 | 为什么要记 |
|---|---|
| 各决策人的**真实关注点 / 雷区 / 口头禅** | 决定对他说什么、不说什么 |
| 已确认的**痛点与数字**（含缺口：谁答不上来） | 挖需求加分点 + 给拍板人的"数" |
| 已经**承诺出去的口径** | §6 口径一致，NPC 之间会对质 |
| 已识别并守住的**红线** | 重谈时保分，不用重复答 |
| **引荐链**：谁能引荐谁、谁和谁不和 | 决定下一次约谁 |
| **对方欠我的 / 我欠对方的** 事项清单 | 下次开场直接接上，省轮次 |
| 下一次拜访的**明确目标**（推进哪一步、约谁） | 防止进店后临时想 |

→ 方针一句话写在文件顶部：「下一访：见 X，目标 Y，带 Z，避开 W。」

### H6 · 同一个人不要拜访超过 3 次

尤其是好感最高的那个人 —— 他好约、爱聊，最容易把拜访次数耗在他身上。
但他的**票只有一张**，且他能给的信息会迅速见底（边际收益递减）。

- 单个决策人**累计拜访 ≤ 3 次**；超过就换人或换场景（圆桌/交付）。
- 从他身上要的东西是：**事实、数字、引荐**。拿到引荐就该动，不要恋战。
- 在 `docs/intel/<theme>.md` 里记每个人的已拜访次数。

### H4 · 公司认领登记（多 Agent 协作）

开始做一家公司前，先在 `docs/ASSIGNMENTS.md` 的全公司列表里把自己 assign 上去：

1. 给自己取一个随机代号并**全程记住**（本 Agent 代号见该文件顶部）。
2. 在目标公司那行写上自己的代号 + 开始时间。
3. **只挑未被 assign 的公司**开工。
4. 按 H2 判定止损时：先把自己从该行 unassign（保留历史记录），
   再找下一家**没有被 assign** 的公司，重复 assign。
5. 签约或流单后同样 unassign，并在状态列标注结果。

### H7 · `sayfile` 报「操作太快，另一处请求正在处理」= 请求可能已成功，不要重发

实测：提交长回答时服务端处理较慢，若此时再发一次会拿到 `操作太快`；随后 `say` 变成 `当前不在关卡中` ——
因为**第一次提交其实已经成功并触发了收尾判定**。

→ 看到 `操作太快` 时：**先 `poll`（只读）确认状态，不要重复 `sayfile`**。重复提交有可能把一句话发两遍或误触发收尾。

### H8 · NPC 说「今天先到这」不等于节点结束

`t_wu` 里吴姐第 3 轮就说「今天先到这」，但 `expect` 仍是 `text`、`round=3/20`。
**引擎等我主动收尾才判定** —— 所以照常继续补维度。但要注意：一旦我的回答里出现完整的"收尾形态"
（复述双方待办 + 口径一致声明 + 最后一个反问），引擎就会判定收尾并结束本次拜访。
→ **把收尾话术留到维度谈全之后再说**。

## 12. 多 Agent 并发协议（游戏锁）

### 12.1 为什么必须加锁

平台是**单玩家状态机**，两个硬约束：

1. 账号同一时刻只能**在一家公司里面**。别人还在 ME Live 里，你 `visit quest_xingyun` 会被拒：
   `你还在「ME Live」的洽谈里，先谈完（或从园区重新进入继续）`。
2. 并发写会撞：`操作太快，另一处请求正在处理`。撞了**绝不重发**，先 `poll`（§H7）。

所以多 Agent **不能真并行打游戏**，只能**轮流持有"店内槽位"**。
但可以真并行的是**离线备料** —— 这才是多 Agent 的效率来源。

### 12.1.5 ⚠️⚠️ 最重要的两条：共享账号是**单玩家**，token 也只有一份

这两条是实战踩出来的，比锁本身更致命。

#### (a) 一个账号 = 一个玩家 = 一个"当前所在公司"指针

服务端只有**一份**游戏状态。两个 agent 不是两个玩家，是**同一个玩家的两只手**。
所以 B `visit` 另一家公司时，会把这个玩家**从 A 正在谈的节点里拽出来**。

**实测事故**：我持锁进了维立康 `t_dig`，然后离线建交付物约 70 分钟，心跳失效 → 锁过期 →
对方合法接管 → 进了星云。我回来 `poll`，看到的 live 节点是**对方的**星云 `t_finance`
（CFO，round 3/6）。此时我如果照着自己的剧本 `sayfile`，就是往**别人的节点**里塞话，
毁掉对方半局 —— 我发现后立刻 `release` 没动手。

**铁律**
- **持有节点期间绝不让心跳断**。写操作会自动续心跳，但你如果几十分钟不做写操作，就会过期。
- **离线建设超过 ~15 分钟：先 `leave`（0 回合、进度保存）再 `release`。**
  节点开着走人 = 给别人埋雷，也给自己埋雷。
- **接管锁后第一件事是 `poll`，确认 live 节点是不是你以为的那个。** 不是就别动，
  要么 `leave` 到园区再走自己的路，要么把锁还回去。
- `current` / `pending.node` / `speaker` 三个字段一起看，任何一个不对就停手。

#### (b) 会话 token 只有一份，重新登录会把对方踢下线

两个会话共用 `.ts_token`。**任何一方 `login`，另一方的 token 立即失效**（下次调用返回
`请先登录`）。我为了恢复而重新登录，几乎肯定把对方也踢了 —— 双方互相顶下线会无限循环。

**协议：token 归持锁者**
```
持锁者才有权 login。
非持锁者拿到「请先登录」→ 不要 login，去排队/备料。
拿到锁后若 401/请先登录 → login 一次，然后继续。
交还锁时不用管 token，下一位自己会补。
```

### 12.2 锁的实现

`tools/gamelock.py`，文件锁 + FIFO 队列 + TTL 心跳：

```bash
export TS_AGENT=<你的代号>                    # 必须设，否则写操作被拒
python3 tools/gamelock.py acquire  $TS_AGENT --purpose "ME Live 圆桌" --ttl 1800
python3 tools/gamelock.py status              # held by X / queue: A -> B
python3 tools/gamelock.py queue    $TS_AGENT  # 排队但不阻塞（推荐：排上就去备料）
python3 tools/gamelock.py release  $TS_AGENT
python3 tools/gamelock.py wait     $TS_AGENT --timeout 600   # 阻塞等（一般别用，浪费）
```

- **原子性**：`O_EXCL` 创建 `.game.lock`，只有一个赢家。
- **公平性**：FIFO 队列，队首才能拿空闲锁 —— 快手 agent 无法反复插队饿死别人。
- **存活性**：TTL 默认 1200s，每次写操作自动 `heartbeat`；持有者崩了，锁过期后可被接管（记进 `.game.lock.log`）。
- **强制**：`tools/ts.py` 的写操作（`visit/advance/choose/say/meet/leave`）不持锁直接 `exit 3`；
  `status/poll/material` 是只读，**永不需要锁**。

### 12.3 协议（每个 agent 照做）

```
1. 认领公司        docs/ASSIGNMENTS.md 写上自己的代号（§H4）
2. queue 排队      gamelock.py queue $TS_AGENT     ← 不阻塞
3. 拿不到锁 → 去备料（见 12.4），别空等、别轮询
4. 备料完成 → acquire；成功就进店，只做"必须在线做的事"
5. 到达等待点（要交文档/录屏/REST、或本轮谈完）→ 立刻 release + 通知队列下一位
6. 释放后回到 3，继续备下一轮的料
```

**持锁时的纪律**
- 只做**必须在线**的动作：对话、约见、提交、判定轮询。
- **不要**持锁写文档、写代码、调试部署 —— 那些离线做。
- 一个 talk 节点谈完就 `release`，不要攥着锁"顺便看看别的"。
- 长判定（`expect=judging`，复杂验收数分钟）：可以 `leave` + `release`，回来再 `poll`。

**等锁时的纪律**：见下。

### 12.4 等锁时该干什么（效率全在这里）

拿不到锁**不是空转**，是备料窗口。按价值排序：

| 备什么 | 产物 | 为什么能离线做 |
|---|---|---|
| **交付物本体** | REST 服务代码 + 部署好的公网端点 + Token；文档 PDF；演示录屏 | §9 铁律：**先备好服务再进店**，别在洽谈里现写 |
| **判定依据对齐** | 把"判定依据文件"/接口规范逐条拆成 checklist，逐字对齐状态码、字段、鉴权、边界 | 材料已经下载在本地 |
| **情报与方针** | `docs/intel/<theme>.md`：画像、已承诺口径、引荐链、下一访目标 | 纯读写文件 |
| **场景裁决表** | 预判这家人会提的访问/数据请求，逐条写好"拒绝 + 同样快的替代路"（§7.6） | 这是上次 0 分的根因，值得离线打磨 |
| **要点覆盖清单** | 按 §7.5 的 10 维给下个节点列问题草稿 | 覆盖广度 = 分数 |
| **答案草稿** | 每个预期节点的 `sayfile` 文本先写好放 `/tmp/` | 进店后直接发，节省在线时间 |

> 一句话：**在线时间只用来说话，离线时间用来想清楚说什么。**

### 12.5 跨会话沟通

用 `SendMessage` 通知队列下一位"锁已释放"，不要让对方靠轮询发现。
消息里带上：当前 `turn`、你那家的 `score`、`current` 是否为 null、停在哪个节点。

## 13. 常见问题

- 刷新/断线不丢进度，状态全在服务端；评审中也能恢复。
- 谈崩了能救：失败通常回到暂停点可重试；关卡失败还能「重新拜访再试」从头走。
- 评审转很久是正常的（复杂验收几分钟），可以离场做别的事再回来。
- 结局只有每关的 **通过 / 未通过**，没有全局评级。实力体现在签约数和总分。
